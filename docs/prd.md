# PRD — Tree Surgery

Nov 3, 2026 · @Chris Doran

## Summary

Each student pastes the team's key question, and the EM checks it first (Stage 1). Once it is OK, the student uploads their issue tree as a PDF or PowerPoint file, and the EM reviews it as read, with no correction step (Stage 2). A Pass ends the run; otherwise the student revises once and gets a direct sign-off. Stage 2 tests two things: strict MECE logic, and whether each split runs with the grain of this client's problem. It reuses Question Time's scaffold. Shared elements are in the Common Module.

## Learning goals

The student learns to break a key question into a tree that is both logically sound and specific to the problem.

| Goal | Why recruiters care |
| --- | --- |
| Decompose a key question into MECE branches | Structuring is the core of every case interview |
| Split each node on the biggest next decision, with the grain of this problem | Separates thinking from template-filling |
| Avoid generic trees that are MECE but useless | Firms want problem solvers, not framework reciters |
| Restructure after critique | Iterating a structure with a senior is daily work on an engagement |

## Users, timing and team model

- **Who:** each student individually.
- **When:** Session 2 on the new case; again on the final case (China). Optional on other owned cases.
- **Release rule:** opened after the team's Question Time submission, since Tree Surgery builds on the key question agreed there.
- **Team model:** individual trees by the Canvas deadline; the team synthesises one tree for its deck.
- **Cases:** v1 is generic only. As in Question Time, the student uploads or pastes the client context (with the same case detector), and the EM judges the tree by the rules, not the specifics of a case. Case configs (reference tree, grain, traps) are a later version.

## Scenario and user flow

In-world: the team has agreed a key question (in Question Time), and the EM wants each team member's draft tree, built on it, before the team problem-solving session.

1. Student enters the access code, name, student ID and course, then uploads or pastes the client context, as in Question Time.
2. Inbox shows the EM's email: "Send me your key question first. Once we've agreed it, send me your draft issue tree by \[deadline\], one page, in our template."
3. Stage 1: the student pastes the key question, with the first-level sub-questions if they carry the target. The EM reviews it. If it isn't OK, the EM's email says why and the student re-enters it (3 attempts a round; after a third, the student reworks it and comes back later with a new one).
4. The student builds the tree offline in the template, to four levels below the key question, with the agreed key question at the root.
5. The student uploads the tree as a PDF or PowerPoint file and, if it has several pages, picks the one with the tree. There is no correction step: the EM reviews the tree as read.
6. Stage 2: the EM's first review arrives, opening with a verdict. A Pass ends the run.
7. Otherwise the student revises the tree and uploads it once more.
8. The EM's sign-off arrives: direct, opening with a sign-off verdict.
9. The student downloads the record PDF and uploads it to Canvas.

## Key question entry and tree upload

The key question is agreed before the tree is uploaded, so the tree is never reviewed on a weak question.

- **Key question:** pasted as text, with optional first-level sub-questions. The upload opens only once Stage 1 says it is OK.
- **Template:** Chris's one-page issue tree template, key question on the left, branches to the right, text in boxes, connector lines. Supplied as a PowerPoint file. Top-down trees are read too.
- **Tree file:** PDF or PowerPoint (.pptx). For a file with several pages or slides, the student picks the one with the tree.
- **Reading:** the model reads the page (the page image and its text layer for a PDF; positioned text and connectors for PowerPoint) into an outline, which only the EM sees. There is no correction step.
- **Unreadable page:** if the tree can't be read (eg a blurred scan, or several trees on one page), the EM says so and the student uploads again. This doesn't use up the revision.
- **Large trees:** a tree of more than 60 boxes is read without its bottom level (never levels 0 to 3), with a note saying how many boxes were left out, so the reading fits the time limit. The EM sees the note.
- **Root:** the agreed key question is the root. If the tree's root differs, the EM reviews against the agreed key question and notes the mismatch.
- **Record:** the EM's reading of each tree is printed as an appendix, so Chris can check reading accuracy in the pilot.

**Pre-launch read test:** the nine calibration trees (PDF and PowerPoint). Every level 1 and level 2 node must be read under the right parent.

**Read test result (3 Nov 2026):** 27 of 27 readings (nine trees, three runs each) placed every level 1 and level 2 node under the right parent. The slowest reading took 17.2 seconds.

## EM review

The EM tests logic first, then usefulness, and flags any tree that passes logic but fails usefulness: "Logically sound, but it could be anyone's tree."

**Build without judgement.** The EM critiques structure only. It never criticises a branch for being illegal, unethical, unrealistic or silly: those judgements decide which branches are cut or parked at prioritisation (v2). A parking branch, such as legal vs illegal, is a valid split.

### Stage 1: key question

The EM reviews the key question and its first-level sub-questions before anything else, using the Question Time checklist. It does not critique the tree until the key question is OK, and in Stage 1 it says nothing about the tree's structure: level 1 is read only for the SMART goal. It fails a test only on a material fault, not a technicality.

| Test | Passes when |
| --- | --- |
| SMART | A measurable target and a time frame appear in the key question or a first-level sub-question. A threshold is measured ("positive operating cash flow"); a duration is a time frame ("$250K for 4 consecutive quarters"). A broad key question is fine if a sub-question carries the SMART goal |
| One question | Not two questions joined by "and". A constraint ("…while…") is not a second question |
| No overlap | Its parts don't overlap (servicing a debt needs the revenue) |
| Open | Not a yes/no question, and no solution built in |
| Clear words | No weak verbs or phrases ("stabilise" with no figure, "evolve", "make better use") |

**Benchmark (for a later case mode; not in v1, never shown to students):** "How can PEIP avoid going bankrupt ever again?", with "How can PEIP generate $100k operating cash flow in the next 18 months?" (the SMART goal) and "How can PEIP build robust governance and organisation?" (the organisational scope).

**If it isn't OK,** the email opens "The key question needs rethinking. Send back to me when you have reworked the tree with a new question." and covers the key question only. As in Question Time, the EM names each fault plainly and gives the model shape, "How can \[Client\] achieve \[quantified outcome\] through \[mechanism\] by \[date\]?", but never writes the team's key question.

**If it is OK,** the EM replies: "That Key Question will work to structure the tree." **After three attempts that aren't OK,** the student is sent away to rework the key question, with the team if they can, and comes back later with a new one: a new round of three attempts. Rounds are not capped, and every attempt and email goes on the record.

### Stage 2: tree

Once the key question is OK, the EM reviews the tree against the tests below.

### A. Logic

| Test | Question |
| --- | --- |
| Mutually exclusive | Do any siblings overlap? |
| Collectively exhaustive | Is anything missing at each level? |
| Answers the parent | Does each level answer the node above it? |
| Consistent split | Does each level use one splitting logic? |
| No single child | Does any node lead to just one branch? If so, consolidate it. |
| Top split size | Does the top split have two or three branches? |
| Clear meaning | Is each label precise enough to judge whether its children are complete and answer it? |
| Same level | Is any sibling a component of another sibling? |

### B. Useful and specific

| Test | Question |
| --- | --- |
| Transplant | Could the first two splits be moved onto another company unchanged? If so, they are generic, which is a mistake at that level (rule 11). |
| Next decision (every node) | Does each node split on the biggest decision you'd make next in that branch, so that each child is one option of that decision? |
| Decision | Would answering each branch change what the client does? |
| Coverage | Later version (case mode) only: does a branch lead to the key issues in the case's reference tree? Not used in v1. |

### C. Grain: symptoms and checks

The next-decision test says where to cut; these symptoms catch cuts that run across the grain. The test behind them: could two analysts work on sibling branches separately, passing at most a short, one-way brief? Apply it at every level, not only the first split.

| Symptom | Signal | EM probe |
| --- | --- | --- |
| Knock-on | Pulling a lever in one branch moves a sibling | "If you raise price, what happens to volume?" |
| Repeated lever | The same action belongs under several branches | "Where else would 'do reading' fit?" |
| Two-way hand-off | A later stage keeps forcing an earlier one to change | "Would 'attract' ever send 'define' back?" |

| Split type | Positive check | EM probe |
| --- | --- | --- |
| Sequential | Each hand-off can be named | "What does 'define' hand to 'attract'?" |
| Parking branch | Parked in one place, with a trigger to revisit | "What would send you back to this branch?" |

### D. Menu of cuts (below the first two splits)

The first two splits must be unique to the problem (rule 11). Below that, the EM can point students to these cuts.

| Type | Cuts |
| --- | --- |
| Mathematical | Revenue/cost (prefer unit economics, rule 8) · frequency/transaction size · cost per click/conversion rate |
| Distinctions | Existing/new (product, customer, business…) · supply/demand · quality/quantity · ethical/unethical (a parking branch, rule 2) |
| Categories | Business · segment · channel · product · country |
| Frameworks | Marketing: 4Ps · organisational: 7S · process: value chain (producer, distributor, retailer, user) · steps 1, 2, 3, 4 · customer journey/funnel · before/during/after |

**Be careful with frameworks.** Some are not independent: the parts of the 4Ps or 7S must be integrated so they fit together. They belong in the twigs, once the big decisions (e.g. target customer and value proposition) are made. Others, such as the 4Cs for strategy, are more independent and complete.

### Review rounds

| Round | Style | Content |
| --- | --- | --- |
| First review | Socratic | Stage 2 only: the key question has already passed Stage 1. Three to five questions pointing at the weakest parts, covering both logic and grain, worst first; one line on what works. Never names the missing branch. It concentrates on the top levels; if the first two splits can't be recovered, every question goes to them (rule 10). |
| Sign-off after revision | Direct | What improved; what still fails, named plainly by its test or symptom; lower-level comments held back from the first review; one lesson for next time. A sign-off of either verdict ends the run |

### First-review verdict

The first review opens with one of four verdicts, checked in this order:

| Verdict | When | Opener |
| --- | --- | --- |
| Key question | Stage 1 fails (see Stage 1: key question) | "The key question needs rethinking. Send back to me when you have reworked the tree with a new question." |
| First cut | The first two splits can't be recovered, e.g. inflow vs outflow (rule 10) | "The first cut needs rethinking. Send back to me when you have reworked it." |
| Rework | The top levels hold, but parts need rework | "Good start, but the tree needs some rework. Send back to me for a quick check when done." |
| Pass | No material issues | "Well structured tree. Go ahead and use this to develop the workplan." |

A Pass ends the run. After a revision, the sign-off opens with one of two verdicts:

| Sign-off verdict | When | Opener |
| --- | --- | --- |
| Signed off | The revision fixes the material faults | "Signed off. Use this to develop the workplan." |
| Not there yet | Material faults remain | "Not there yet. Take what's left to the team session." |

**Reference tree use.** Later version (case mode) only. Chris's example tree is a reference, not an answer key. A different but valid structure passes if it covers the same key issues. The EM never reveals or describes the reference tree.

## Authoring template per case

Later version (case mode) only: Chris adds a Tree Surgery section to the case config file. Not in v1.

```
TREE SURGERY
1. Reference key question and SMART sub-question (the Stage 1 benchmark; never shown)
2. Example strong tree (to sub-issue level)
3. Key issues a strong tree must reach (3–5), each with:
     • the issue
     • why it matters to the answer
4. The grain of this problem:
     • the biggest next decision at each main node
     • the hand-off between stages, for any sequential split
     • tempting cuts across the grain, each with the interaction that breaks it
5. Generic tree to call out (the typical template answer for this case)
6. Common traps (e.g. splitting by department rather than by driver)
7. In-world email: deadline wording, any context the EM adds
```

## Calibration

The usefulness tests encode Chris's judgement, so the EM is calibrated against his verdicts before launch.

- **Set:** about 15 trees: Chris's three teaching examples (wealth, final grade, boyfriend/girlfriend), 8–10 past student trees, and contrastive pairs written at the edges of the rules.
- **Answer key:** Chris's verdict on each tree, written before he sees the EM's, plus the planted flaws in each teaching example.
- **Result (PEIP, three runs):** the EM's verdicts matched Chris's on all nine trees (eight student trees and Chris's good tree). 9 of 11 tree points were in the emails and 2 were held back, which has been fixed. This is in-sample: a holdout test on trees from another case is still to run.
- **Misses:** each becomes a rule change or a case-config entry; then rerun.

### Rules from calibration so far

The key question is level 0, so the first split is level 1. "First two splits" means levels 1 and 2.

1. **Independence is about the interface, not the order.** A sequence runs with the grain when each stage hands the next a short, one-way brief (e.g. target customer → product and media; a heist planned as get in, get the money, get out, fence).
2. **Build without judgement, then judge at prioritisation.** The EM never criticises an idea's ethics, legality or taste. A parking branch (e.g. legal vs illegal) is a valid split.
3. **Teaching examples carry planted flaws** (e.g. gambling missing from one-off cash in the wealth tree). Each is a check the EM must catch.
4. **Split each node on the biggest decision you'd make next in that branch** (selling → what to sell? asking → who to ask? team grades → team selection, team operation).
5. **Split on the metric in the key question.** If the key question says cash flow, cash flow is the root; profit sits inside operating cash flow, not beside it (PEIP, Group 1).
6. **Cut so that parking is clean.** Options likely to be parked (unsustainable sources, businesses with no competitive advantage) get their own branch, so they can be parked whole: non-operating cash flow, with capex separated early; non-jam business before the jam channel split (PEIP).
7. **Independence trumps a pure split logic.** A branch of a different kind (e.g. organisation and governance) passes if its solutions are almost entirely independent of the other branches. The two-analyst test decides; the consistent-split test and rule 4 are advisory. Independence is judged as stated: "cash control" built from accounting and hiring flows through inflow and outflow, so it fails (PEIP, Group 2). Scope the branch as organisation and governance, not narrowly as "structure" (Group 7).
8. **Split by unit economics, not revenue vs cost.** Contribution by unit (volume × (price − variable cost per unit)), then fixed costs. A revenue/cost split puts a unit's price and its variable cost in different branches, so every unit decision appears in both (knock-on). Probe: "If PEIP pushes more jam through wholesale, which of your branches change?" Working capital stays inside each unit too: trade terms are negotiated together with price and cost, so don't separate it early. Once a single business is isolated (e.g. under "jam"), revenue vs cost is appropriate, and shared manufacturing and overhead costs can sit in their own branch (good-tree test).
9. **Before flagging a gap, check whether existing branches already move it.** An outcome that only moves through other levers is not a missing branch (PEIP: seasonality improves only through channel mix, so it needs no branch of its own).
10. **Triage: fix the root first.** The first review concentrates on getting the top levels right; lower-level comments wait for the sign-off. If the first two splits can't be recovered (e.g. cash inflow vs outflow, too interwoven), all feedback goes to those two splits; nothing below them (PEIP, Group 2). The review opens with one of four verdicts (see First-review verdict). Faults at levels 1 and 2 are still raised, not held as moot because the tree will be re-cut.
11. **The first two splits must be unique to this problem.** A generic cut there is a mistake (inflow/outflow is the worst; also revenue/cost, OPEX/COGS, labour/materials/overhead). Generic cuts, such as the Tree Cuts menu, are fine lower down.
12. **No single-child nodes.** A branch that leads to one branch is consolidated.
13. **Two or three branches at the top split.** Four or more makes an independent, complete split very hard to keep; longer lists (e.g. channels) belong lower.
14. **Pin down what a node means before judging its split.** An ambiguous label can make the children incomplete under one reading and off-question under the other. PEIP Group 4, "year-round revenue": if it means total revenue, "new off-season revenue" leaves out existing off-season revenue (drop "new"), and the split is complete but not very useful; if it means the minimum regular monthly revenue, it is specific to the key question, but "maximise peak season" no longer fits. Probe: "What does 'year-round revenue' mean?" Read each node in the light of its parent, charitably: "Exit?" under "changing businesses" means exiting a business, so it doesn't overlap a branch about running the existing ones (good-tree test).
15. **Strategic cuts near the top, tactical cuts in the twigs.** Exiting or selling a business sits high in the tree; "run a Twitter campaign for cruise ship passengers" is a twig.
16. **What the key question prunes never appears in the tree.** If the key question says operating cash flow, non-operating cash flow is absent, not parked. Parking (rule 6) is only for options the key question leaves in. "Sustainable" cash flow leaves out capital structure, financing and one-offs (good-tree test).
17. **Split revenue first by target customer.** Product, channel, price and promotion decisions flow from it. When each channel serves a unique target customer, the two splits are the same, so use whichever matches the client's own language (PEIP: channel).
18. **A fluffy key question needs SMART sub-goals at the first split** to ground the solutions (PEIP Group 6: "long-term financial viability").
19. **The tree maps the solution space, not diagnostics.** Diagnostic questions ("Which segments generate the highest margin?") decide which branches to pursue at prioritisation; they are not embedded in the tree.
20. **Vague verbs hide the decision.** "Streamline" (cut cost?), "focus on" (invest in?), "optimise": the EM asks what action is meant (extends rule 14). "Stabilise" needs a target, such as a C$k figure, to mean anything (Group 7).
21. **Deep enough to map the problem.** A tree that stops before the options are concrete is too light (PEIP Group 6 needed another level). Four levels below the key question is enough. Not every branch needs full depth: expand the branches most likely to hold solutions, and leave long shots shallow (good-tree test).
22. **Critique a weak key question first.** If the key question is not very good (double-barrelled, overlapping, fluffy), the EM critiques it, and does not critique the tree until the key question is OK (Stage 1) (PEIP Group 7: "sustainable profitability and long-term growth" compresses to "sustainable cash flow"). A constraint is not a second goal: a key question that limits its goal ("…while…") is not double-barrelled.
23. **Siblings sit at the same level.** If one sibling is a component of another, either it moves under the other, or the split leaves out what lies between (PEIP Group 7: gross margin beside capital structure and cash flow; either gross margin belongs under cash flow, or every cost between COGS and capital is missing).
24. **An overlapping key question breaks the tree at once.** If its parts overlap, the first split inherits the overlap and the solutions in each half overlap. The EM critiques the key question, not the tree (PEIP Group 8: servicing the $685K debt requires sufficient year-round revenue).
25. **Nodes are "How can…" questions and don't restate inherited limits.** A node question does not spell out every constraint from the branches above; written out in full it would be too clunky. The EM does not criticise a node for leaving them out.
26. **Don't be harsh: pass a good tree.** A tree passes when its first two splits are specific and independent, it isolates the units, and its most promising branches reach concrete options. Shallow long shots and imperfect twigs don't stop a pass. Raise a point only if it survives the most sensible reading and fixing it would change what the team analyses next (good-tree test).

## Risks, success measures and open questions

| Risk | Mitigation |
| --- | --- |
| The EM misreads the uploaded tree (no correction step) | Template; pre-launch read test; the EM says when a page can't be read; the record shows how the EM read the tree |
| EM penalises valid but unusual structures | Reference tree framed as coverage check; pilot on varied past trees |
| Socratic questions too vague to act on | Each question must point at a named node or level |
| Students optimise for the checker | Usefulness tests weigh more than formal MECE |

**Success measures:** pilot pass marks met; all generic test trees flagged; team trees in decks show more case-specific first splits than in previous years.
